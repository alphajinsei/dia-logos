・オントロジーの説明が、よく経理の話を例にされるのは何か理由があるのでしょうか。私はエンジニアに近い職種なのでこの例自体にあまりなじみがなくて、身の回りにある「業務」で言うと、システムの月次リソース報告資料を作る、とか言ったのが思い浮かぶのですが。

## 1. オブジェクト指向とのアナロジーについて

### 対応はほぼその通りです

正確に対応させると次のようになります。

| オントロジー | オブジェクト指向 |
|---|---|
| Object Type（「予算」という種類） | class |
| Object（「営業部2026年度旅費の予算」という個体） | instance |
| Property | フィールド、プロパティ |
| Link | 他のインスタンスへの参照を持つフィールド |
| Action | 状態を変えるメソッド |
| Function | 状態を変えないメソッド（getter、計算プロパティ） |

似ているのは偶然ではなく、両者には共通の祖先があります。最初のオブジェクト指向言語 Simula（1967）は、名前のとおり**現実世界をシミュレーションするため**の言語でした。「現実のモノをそのままコード上のモノとして書けば見通しがよくなる」というのが、オブジェクト指向の出発点です。また、AI研究のフレーム理論（Minsky, 1974。概念をスロット＝属性の束として表現する）は、オブジェクト指向と古典オントロジーの両方に影響しています。第1部で触れた DDD は、「オブジェクト指向を業務のモデリングに本気で使う」方法論だと捉えるとよいです。

### ただし「オブジェクト指向が中間言語として適当」は半分だけ正しい

いただいた読み方を少し直すと、こうなります。

> 業務担当者とエンジニアの共通言語には、**「モノ」と「モノに対する行為」で世界を記述する言語**が適している。オブジェクト指向はその発想を、プログラマ向けに最初に実装したものである。

一段深く掘ると、両者が共通して借りているのは**自然言語の文法**です。

- Object → 名詞
- Property → 形容詞（「予算額が120万円の」）
- Link → 「〜の」「〜に属する」
- Action → 動詞
- Function → 判断（「消化率が高い」）

人間はもともと「何が・何を・どうする」で世界を認識しています。この文法に沿っているから、業務担当者にも読め、同時にエンジニアが実装に落とせます。中間言語として機能する理由は、オブジェクト指向だからではなく、両者がすでに共有している文法に乗っているからです。

### オブジェクト指向と違う点

オブジェクト指向の感覚のままオントロジーを作ると、つまずく点が4つあります。むしろここに、オントロジーが何を重視しているかが表れています。

**① 動詞がクラスに属さない**
オブジェクト指向では、メソッドはどれか1つのクラスに属します。では `予算を流用する(元予算, 先予算, 金額)` はどちらの予算のメソッドでしょうか。`月次を締める(部門, 年月)` は部門と大量の仕訳を同時に変えます。オブジェクト指向では「このメソッドはどのクラスに置くべきか」という設計上の悩みが必ず出ます（銀行の振込を `口座A.振込(口座B)` にするか `振込サービス` にするか、という有名な問題です）。

オントロジーでは、Action は**特定の Object に属さない独立した要素**で、引数として複数の Object を受け取ります。業務担当者の頭の中でも、「流用」は予算Aの持ち物ではなく、2つの予算の間で起きる出来事だからです。

**② カプセル化をしない**
オブジェクト指向は内部状態を隠し（private）、メソッド経由でしか触らせません。オントロジーは逆で、**状態はすべて公開**されています。誰でも Property を読め、Link をたどり、集計できます。組織全体で同じ世界を見ることが目的なので、隠す理由がないからです。

ただし「書き込みは Action 経由に限る」という点だけは残っています。つまり、カプセル化のうち「読み取りを隠す」部分は捨て、「書き込みを制御する」部分だけを、権限管理として残した形です。

**③ 関係が双方向にたどれる**
オブジェクト指向の参照は片方向のポインタです。`仕訳.部門` はたどれますが、「この部門の仕訳すべて」を取るには、別にコレクションを持つか検索するしかありません。オントロジーの Link はグラフの辺なので、どちらからでもたどれ、検索もできます。この点はDBのリレーションに近いです。

**④ インスタンスがメモリ上ではなく、既存の実データの上にある**
オブジェクト指向では、class がデータの形を定義し、インスタンスはプロセスの中で生まれて消えます。オントロジーでは、**データはすでに会計システムや Excel の中に存在**しています。オントロジーはそのデータに後から被せる「解釈の層」です。DBで言えば、テーブル定義ではなくビューに近いものです。

まとめると、

> オントロジー ＝ オブジェクト指向の「名詞」はそのまま使い、
> 動詞をクラスから独立させ、カプセル化を外して誰でも読めるようにし、
> 関係をグラフとしてたどれるようにし、組織の実データに永続的に張り付けたもの

となります。

## 2. なぜ経理の例なのか

これは私の説明のせいで、誤解を招いてしまいました。**オントロジーの解説で経理がよく使われる、ということはありません。** Palantir 自身の例は、航空（機体・フライト・空港）、サプライチェーン（部品・工場・発注）、製造などが中心です。今回経理を例にしたのは、最初に経理の月次予算集計の話をいただいたので、それに合わせたためです。

ちなみに、経理を例にすると説明しやすい面はあります。複式簿記は500年前からある「業務の形式モデル」で、勘定科目は分類体系、仕訳は出来事の記録、試算表は導出値になっています。すでに半分オントロジーになっている業務だということです。

### 月次リソース報告は、題材としてとても良いです

挙げていただいた「システムの月次リソース報告資料を作る」でも、オントロジーの論点がすべて出てきます。ざっと当てはめてみます。

- **Object**：システム、ホスト、月次報告、増強案件
- **Link**：ホスト →所属→ システム、月次報告 →対象→ システム
- **Property**：ホスト.vCPU数、閾値.警告値
- **Function**：月間ピークCPU使用率、前月比、枯渇予測日
- **Action**：報告を確定する、増強を起票する、閾値を変更する

特に面白いのは、**「何を1台と数えるか」という、Object の自己同一性の問題**が正面から出てくることです。

- 物理ホスト、VM、Kubernetes の Node、Pod のうち、「サーバー」はどれか（原則C：多義語は分ける）
- Pod は再起動のたびに名前が変わります。これを Object として追跡すべきでしょうか。安定した単位は Deployment ではないか（原則D：業務が変わらない限り変わらない単位で切る）
- VM が別のホストにライブマイグレーションしたとき、「ホスト→VM」の Link はどう扱うか（関係に期間があるなら、Object として実体化する）
- 「報告書に載せた先月のピーク値」は Function か Property か（判定テストの例外：凍結したスナップショット）

どれも、CKA をお持ちの方なら直感的に答えが分かる問いのはずです。

### 第2部の題材をどうするか

2つの題材には、練習できることに違いがあります。

| 題材 | 練習できること |
|---|---|
| 月次リソース報告（ご自身の業務） | 自分で正解を判断できるので、**分類の方法そのもの**に集中できる |
| 経理の予算集計（知らない業務） | **知らない業務をヒアリングで掘り出す**練習になる。本来のFDEの状況に近い |

おすすめは、**リソース報告で方法を身につけてから、経理でヒアリングを練習する**という二段構えです。方法と聞き取りを同時に練習すると、つまずいたときに、分類の仕方で迷っているのか、業務を知らないことで迷っているのかを切り分けられません。

## 1. Function も Object には属しません

ご質問の整理でほぼ合っています。Palantir の Ontology の構造を正確に言うと、5つの要素は**どこで定義されるか**が次のように違います。

| 要素 | 定義される場所 | Object との関係 |
|---|---|---|
| Property | Object Type の定義の中 | **1つの Object Type に属する** |
| Link | 2つの Object Type を指定して、独立に定義される | **2つの Object Type のペアに属する**（どちらか片方には属さない） |
| Action | 独立に定義される。引数で Object を受け取る | **属さない**。引数の型として参照するだけ |
| Function | 独立したコードとして書かれる。引数で Object を受け取る | **属さない**。引数の型として参照するだけ |

「属する」かどうかは、実は**いくつの Object に関わるか（項数）**の問題として見るとすっきりします。

- 1つの Object だけに関わる → その Object に属する（Property）
- 2つの Object に関わる → ペアに属する（Link）
- 任意の数の Object に関わる → どれにも属さず独立する（Action・Function）

`消化率(予算)` のように引数が1つだけの Function もあります。これは Object に属させることもできそうに見えます。それでも独立させているのは、`着地見込(部門, 年月)` や、何百件もの仕訳を集計する Function と**同じ仕組みで扱うため**です。

### オブジェクト指向の「属する」の正体

実は、オブジェクト指向の「メソッドがクラスに属する」も、項数の話で説明できます。Python ではこれがはっきり見えます。

```python
budget.transfer(other, amount)     # メソッド呼び出しは
Budget.transfer(budget, other, amount)  # 実はこれの省略記法
```

メソッドとは「第1引数（`self`）だけを特別扱いした関数」です。オブジェクト指向は、**どの操作にも必ず1つ主役の引数を選ぶ**という設計です。オントロジーは、**引数を特別扱いしない**という設計です。違いはこの一点で、ここから「なぜそうするのか」という2つ目のご質問につながります。

## 2. なぜこの違いが生まれるのか

「相手にする世界の性質が違うので、それぞれ都合の良い形にした」というご推測のとおりです。具体的には4つの違いがあり、根本的なものから順に挙げます。

### (a) 主語が誰か

これが最も根本的な違いです。

オブジェクト指向の Object は**行為者**です。Alan Kay（オブジェクト指向の提唱者の一人）は、オブジェクトを互いにメッセージを送り合う小さなコンピュータ、生物の細胞のようなものとして考えていました。`口座.引き出す()` では、口座が主語として自分で振る舞います。

オントロジーの Object は、**行為を受ける対象**です。英語の Object はまさに文法の「目的語」の意味です。では主語は誰かというと、**Action を実行する人間や AI** です。

```
オブジェクト指向:  予算A.流用する(予算B, 100万)   ← 予算Aが主語。業務担当者の感覚と合わない
オントロジー:      （田中さんが）予算Aから予算Bへ100万円を 流用する
                    主語は実行者、予算A・予算Bはどちらも目的語
```

主語は Action の実行者として、権限チェックと監査ログに記録されます。Object はどれも同格の目的語なので、どれか1つに動詞を所属させる理由がありません。前回お話しした「自然言語の文法」の話で言えば、オントロジーのほうが業務担当者の話し方にそのまま沿っています。

### (b) 世界を自分で設計するのか、すでにある世界を記述するのか

プログラムの世界は、プログラマが**自分で設計できます**。だから、なるべく操作が1つのオブジェクトの中で完結するように切り分けられます。うまく切り分けられたかどうかが、良い設計の基準になります。

業務の世界は**すでにあって、変えられません**。流用には2つの予算が、締めには部門と大量の仕訳が、約定には顧客・銘柄・口座が関わります。現実の出来事は、もともと複数の当事者の間で起きるものです。そのうち1つを主役に選ぶのは恣意的で、業務担当者には意味が通じません（原則A に反します）。

物理で言えば、ラグランジアンの**相互作用項**に当たります。電子の自由場の項は電子に属しますが、電子と光子の相互作用項 $e\bar\psi\gamma^\mu\psi A_\mu$ は電子にも光子にも属さず、両者をつなぐ独立した項です。Property は自由場の項、Action は相互作用項だと考えると分かりやすいです。

さらに、**守るべき整合性も複数の Object にまたがります**。流用の前後で「予算Aと予算Bの合計は変わらない」という条件は、運動量保存と同じ構造をしています。この条件は予算Aにも予算Bにも属さず、相互作用（流用という Action）の側に属します。オブジェクト指向がメソッドをクラスに置くのは、クラスが自分の内部の整合性を自分で守るためでした。整合性が複数の Object にまたがるなら、それを守る仕組みも Object の外、つまり Action に置くのが自然です。Action がトランザクションの単位になるのはこのためです。

### (c) 何が増えていくのか

ソフトウェア工学には **Expression Problem** という有名な問題があります。

- オブジェクト指向は、**新しい種類（クラス）を足すのは簡単**です。既存のコードに手を入れず、サブクラスを1つ追加するだけで済みます。その代わり、**新しい操作を足すのは大変**です。全クラスにメソッドを追加して回る必要があります。
- 操作を独立させる設計（関数型など）はこの逆です。操作を足すのは簡単で、種類を足すのは大変です。

どちらの設計が良いかは、**どちらの方向に拡張していくか**で決まります。

業務オントロジーでは、Object の種類はあまり変わりません（原則D で、変わらない単位に切っているからです）。一方で、**問い（Function）と操作（Action）は際限なく増えます**。部長が新しい切り口で見たいと言う、監査が別の集計を求める、AI エージェントに新しい仕事をさせる、といった具合です。だから、増えていく側である Function と Action を独立させ、Object を触らずに追加できるようにしてあります。

### (d) 誰が持つのか

オブジェクト指向では、クラスとそのメソッドは同じチームが持つのが普通です。

オントロジーでは、Object の定義は元データの持ち主やオントロジー管理者が持ち、Function は経理チーム・経営企画・AI の開発者など、**利用者側の多くのチームがそれぞれ書きます**。しかも、「着地見込」の計算方法は経理と部長で違うかもしれません。Function が Object から独立していれば、**同じ予算に対して複数の解釈を並べて共存させられます**。Object に属させると、正しい定義を1つに決めなければならなくなります。

## (c) オブジェクト指向と関数型の違い、Expression Problem

### 「大変」の中身

ご理解のとおり、「既存クラスのコードを触らざるをえない」ことを指して大変と言っています。触ることの何が問題かというと、次の3点です。

1. **修正が散らばる**：クラスが10個あれば、10ファイルを直すことになります
2. **触れないコードがある**：クラスが他チームの持ち物やライブラリの中にあると、そもそも修正できません
3. **動いているものを壊すリスクがある**：修正したクラスはすべてテストし直しが必要です

新しいクラスを足す場合は、ファイルを1つ追加するだけで既存のものには触りません。この差が問題になります。

### 具体例：リソース報告のコードで比べる

VM と DB という2種類のリソースに、「月額コスト」と「報告書の1行」という2つの操作がある場合を考えます。

**オブジェクト指向**：データと操作を、種類ごとにまとめます

```python
class VM:
    def __init__(self, vcpu, mem): self.vcpu, self.mem = vcpu, mem
    def cost(self):        return self.vcpu * 3000 + self.mem * 500
    def report_line(self): return f"VM {self.vcpu}vCPU"

class DB:
    def __init__(self, storage): self.storage = storage
    def cost(self):        return self.storage * 20
    def report_line(self): return f"DB {self.storage}GB"
```

**関数型**：データはただの値の組にして、操作を関数としてまとめます

```python
@dataclass(frozen=True)
class VM: vcpu: int; mem: int        # データだけ。メソッドはない
@dataclass(frozen=True)
class DB: storage: int

def cost(r):                          # 操作ごとに関数を1つ作り、種類で場合分けする
    match r:
        case VM(): return r.vcpu * 3000 + r.mem * 500
        case DB(): return r.storage * 20

def report_line(r):
    match r:
        case VM(): return f"VM {r.vcpu}vCPU"
        case DB(): return f"DB {r.storage}GB"
```

ここに2種類の変更を加えてみます。

| 変更 | オブジェクト指向 | 関数型 |
|---|---|---|
| 種類を足す（Storage を追加） | `class Storage` を1つ追加するだけ。**既存コードは触らない** | `cost` と `report_line` の**両方に** `case Storage()` を追加する |
| 操作を足す（CO2排出量を追加） | VM・DB の**両方に** `def co2()` を追加する | `def co2(r)` を1つ追加するだけ。**既存コードは触らない** |

### 本質は「表をどちら向きに切るか」

これは、種類×操作の**表をどちら向きに切ってファイルに収めるか**の違いです。

```
              cost()   report_line()   co2()  ← 操作
    VM        [    ]   [          ]   [   ]
    DB        [    ]   [          ]   [   ]
    Storage   [    ]   [          ]   [   ]
    ↑種類
```

どちらの書き方でも、表のマス目はすべて埋めなければなりません。

- オブジェクト指向は**行ごとに**まとめます（1クラス＝1行）。だから行を足すのは簡単で、列を足すと全行を触ることになります
- 関数型は**列ごとに**まとめます（1関数＝1列）。だから列を足すのは簡単で、行を足すと全列を触ることになります

行列のメモリ配置における row-major と column-major の違いと同じ構造です。row-major なら行の追加は末尾に書き足すだけですが、列を追加すると全行を詰め直すことになります。**両方向の追加を同時に簡単にする方法はない**、というのが Expression Problem です（1998年に Philip Wadler が名前を付けました）。

### 関数型プログラミングとは何か

上の例は「データと操作を分ける」という一面だけでした。関数型の中核にある考え方は次の3つです。

1. **純粋関数**：出力が入力だけで決まり、外の何も書き換えない。数学の写像 $f: X \to Y$ と同じです。`cost(vm)` は何度呼んでも同じ値を返し、何も壊しません
2. **不変データ**：データは書き換えず、変更が必要なら新しい値を作る（上の `frozen=True`）
3. **関数も値として扱う**：関数を引数に渡したり、組み合わせたりできる

オブジェクト指向との違いを物理で言うと、オブジェクトは**内部状態を持つ系**です。同じ入力でも、過去の履歴で応答が変わります（ヒステリシスを持つ系）。純粋関数は**状態を持たない写像**です。状態がなければ、結果の予測もテストも並列実行もずっと簡単になります。

実は、身近なところに関数型はあります。

- **Excel の数式**：各セルは、他のセルを入力とする純粋関数です。世界で最も広く使われている関数型言語だとも言われます
- **SQL の SELECT**：元のテーブルを書き換えずに、新しい結果を導きます
- **Terraform**：「こうあるべき状態」を宣言し、手順を書きません。宣言的という点で同じ系統の考え方です

歴史的には、Church のラムダ計算（1930年代）を源流に、Lisp（1958）、ML、Haskell と続きます。今では JavaScript・Python・Rust などの主流言語が、関数型の書き方を部分的に取り込んでいます。

### オントロジーは関数型に近いのか

**近いです。** しかも、関数型の良い形がそのまま現れています。

| 関数型の考え方 | オントロジー |
|---|---|
| データは振る舞いを持たない値の組 | Object は Property と Link の組で、公開されている |
| 純粋関数で新しい値を導く | **Function**：読むだけで、何も書き換えない |
| 副作用（書き込み）は端に寄せ、限られた場所に閉じ込める | **Action**：書き込みは、定義された Action だけに閉じ込める |

関数型には「純粋な計算を中心に置き、副作用は外側の薄い層に閉じ込める」という定石があります（functional core, imperative shell）。オントロジーは、この定石を組織の規模でやっていると見ることができます。

「Function と Action を Object に内包しないことの意味がここにあるのか」というご質問には、**はい、4つの理由のうちの1つがこれです**、とお答えします。操作と問いが増え続ける世界では、列方向に拡張しやすい形のほうが有利です。

関数型の弱点である「種類を足すのが大変」の方は、オントロジーでは次の2点で抑えられています。

- 原則D によって、Object の種類はあまり変わらないように切っている
- Function は引数の型が特定の Object Type に決まっているので、新しい種類を足しても既存の Function には影響しないことがほとんど

複数の種類をまとめて扱いたい場合のために、Palantir には共通の型を定義する Interface という仕組みもあります。

## (d) 2つのアナロジーについて

### プロジェクト報告の話

構図はまったく同じです。そしてこの例は、**なぜ毎回つらいのか**も説明してくれます。

今は「ご本尊」が頭の中にしかありません。そのため、報告のたびに記憶から手作業でスライドを組み立てることになります。これは、Object が定義されていない状態で、Function の出力を毎回手で計算しているのと同じです。もしプロジェクトが明示的な Object（目的、決定事項、課題、進捗、リスク……）として書き出されていれば、「部長向け」「技術責任者向け」はそれぞれ Function になり、LLM で生成できます。しかも、全部が同じ一つの源から導かれるので、**相手ごとに言っていることが食い違うことがなくなります**。これは実はオントロジーと LLM の良い使い道の一つです。

### 多様体と射影の話

これはかなり正確な対応で、量子力学で言うとさらにぴったり当てはまります。

- **状態ベクトル** $|\psi\rangle$ が Object です
- **観測量**（演算子）が Function です。同じ状態に対して、観測量はいくつでも定義できます
- どの観測量も、単独では状態を特定しません。状態を特定するには、**互いに独立な観測量を十分な数そろえる**必要があります（完全系）

一つ付け加えると、観測する側は射影を通してしか対象を知ることができません。ですから、**一つの対象から、互いに独立で、しかも矛盾しない射影がたくさん取り出せること**自体が、奥行きがあることの観測可能な証拠になります。学歴・資格・説明のうまさが、それぞれ別々の軸でありながら一つの人物像として整合している、ということがそれに当たります。

## DDD と CQRS の歴史

どちらも、「オブジェクト指向で業務を書くとうまくいかない」という問題への答えとして出てきたものです。

### 1. 前史：データと手続きを分けていた時代（1960〜80年代）

COBOL と DB で作られた業務システムの時代です。データはファイルや DB にあり、**バッチプログラムや手続き（プロシージャ）がそれを外から読み書きします**。従来の勘定系・バッチの世界そのものですね。

構造だけ見ると、実はオントロジーに似ています（データと操作が分かれています）。ただし、手続きの名前は `JOB0123`、テーブルは `T_JNL_DTL` のように業務の言葉になっておらず、**意味は仕様書と担当者の頭の中にしかありません**でした。

### 2. オブジェクト指向の約束（1970〜90年代）

Simula（1967）、Smalltalk（1970年代）、C++、Java（1995）と普及していきます。約束は「現実世界をそのままオブジェクトとして書けば、業務とコードが一致する」というものでした。

### 3. 約束が果たされなかった（1990〜2000年代）

実際の業務システムでは、次のような形になりがちでした。

- クラスはデータの入れ物で、getter と setter しか持たない
- 業務ロジックは `〇〇Service` というクラスに手続き的に書かれる
- 設計の中心は DB（ER図）で、クラスはテーブルの写し

結局、前史の「データと手続き」がオブジェクト指向の文法で書かれていただけでした。Martin Fowler はこれを **ドメインモデル貧血症**（Anemic Domain Model, 2003）と呼んで批判しています。そして、コードの言葉と業務の言葉は相変わらずずれたままでした。

### 4. DDD：ドメイン駆動設計（2003年、Eric Evans）

新しいプログラミングの方式というより、**複雑な業務をどうモデリングするかという方法論**です。書籍『Domain-Driven Design』で体系化されました。主な考え方は次のとおりです。

- **ユビキタス言語**：業務担当者との会話で使う言葉と、コードの中の名前を一致させる（オントロジーの原則A と同じです）
- **知識の噛み砕き**（knowledge crunching）：開発者が業務の専門家と繰り返し対話し、一緒にモデルを作っていく。ご自身が最初に考えていた「①と②の間を埋める活動」とほぼ同じものです
- **エンティティと値オブジェクト**：自己同一性を持つもの（予算、仕訳）と、値でしかないもの（金額「120万円」）を区別する。Object と Property の区別に当たります
- **集約**：一つのトランザクションで一緒に変更される Object のまとまり。整合性の境界です
- **ドメインサービス**：どのエンティティにも属さない操作（振込、流用）。前回の話の「動詞がクラスに属さない」を、オブジェクト指向の中で認めたものです
- **境界づけられたコンテキスト**：同じ「顧客」でも、営業部と請求部門では意味が違う。だから**組織全体で一つのモデルを作ろうとせず**、意味が一貫する範囲ごとにモデルを分ける

最後の点は、オントロジーとの**緊張関係**として面白いところです。DDD は「組織全体で一つのモデルは無理だから分けよ」と言い、オントロジーは「組織全体で一枚の層を作れ」と言います。オントロジーはこれを、原則C（多義語は名前を分ける）で解決しています。コンテキストを分ける代わりに、一枚の中で「見込客」「契約者」「請求先」と別の名前を与えるわけです。

### 5. CQRS：コマンドとクエリの責務分離（2010年頃、Greg Young）

源流は、Bertrand Meyer の **CQS 原則**（1988）です。「メソッドは状態を変える（コマンド）か、値を返す（クエリ）かのどちらか一方だけにせよ」というものです。

CQRS はこれを、メソッド単位からシステムの構造全体に広げました。

- **書き込み側**：業務ルールを厳密にチェックするコマンドの世界。種類は少なく、整合性が命です
- **読み取り側**：画面・帳票・ダッシュボードごとに最適化した、多数のビューの世界。種類は多く、形はばらばらです

動機は、業務システムでは**読み取りのほうが圧倒的に多く多様で、書き込みは少なく厳密**だということです。一つのモデルで両方をこなそうとすると、両方が中途半端になります。

CQRS はよく **イベントソーシング** と組み合わせて使われます。これは、状態そのものではなく「起きた出来事」を追記だけで記録し、現在の状態はそこから計算する方式です。そして、この読み取り用の計算結果を、専門用語で **プロジェクション（射影）** と呼びます。多様体の話と用語まで一致しています。

ここで2つ目の疑問（なぜ経理の例か）に戻ると、**複式簿記こそが最古のイベントソーシング**です。仕訳は消さずに追記だけを重ね、間違えたら取消仕訳を追加します。残高や試算表は、仕訳から計算されるプロジェクションです。証券で言えば、約定がイベントで、建玉・残高がプロジェクションです。

### 流れのまとめ

| 年代 | 出来事 | 解こうとした問題 |
|---|---|---|
| 1960〜80年代 | COBOL＋DB、バッチ | 業務を機械化する（意味は仕様書と人の頭の中） |
| 1967〜1990年代 | オブジェクト指向 | 現実をそのままコードに写したい |
| 1976 | ER モデル | データの構造を業務に合わせたい |
| 1988 | CQS 原則 | 変更と問い合わせを混ぜない |
| 1998 | Expression Problem の命名 | 種類と操作、どちらを拡張しやすくするか |
| 2003 | DDD | コードの言葉と業務の言葉を一致させたい |
| 2003 | 「ドメインモデル貧血症」批判 | オブジェクト指向の約束が果たされていない |
| 2010頃 | CQRS、イベントソーシング | 読み取りと書き込みで、必要な性質が違う |
| 2010年代〜 | 業務オントロジー | 上記を、既存のデータの上で組織全体に対して行う |

こう並べると、業務オントロジーは次のようにまとめられます。

> DDD の「ユビキタス言語」と、CQRS の「Action（コマンド）と Function（クエリ）の分離」を、
> 新しく作るアプリの中ではなく、**すでにある組織のデータの上に**、組織全体で一枚として被せたもの

＞Expression Problem
これはなかなか良い説明だったと思います。「種類×操作の表をどちら向きに切ってファイルに収めるかの違い」という説明がしっくり来たのと同時に、業務、あるいはシステムにおける世界観は、種類（オブジェクト）と、操作の２軸で構成されている、という点に驚きました。そもそも２軸しかない、という点が新鮮でした。確かに言われてみるとそうですね。実際のシステムを思い浮かべると、DB上のデータと、それに対する読み出しと書き込みしか操作は存在しないわけで。
それらのどちらを軸に切り出すかが、オブジェクト指向と、関数型プログラミングの根本的な思想の分かれ目ということですね。両方の追加を同時に簡単にする方法はないのが、expression problemだという主張もよく理解できました。

＞4. DDD：ドメイン駆動設計（2003年、Eric Evans）
この話を聞いて思ったのですが、オントロジーの概念はDDDから出発して対比したほうが理解が深まるでしょうか。境界付けられたコンテキスト、という概念が、オントロジーとは異なる点だが、それ以外はDDDをベースラインにした概念なのでしょうか。

＞5. CQRS：コマンドとクエリの責務分離（2010年頃、Greg Young）
CQS原則は、メソッドは、更新か参照かのどちらかだけにすべきで、まとめて実行するようなメソッドは筋が悪い、ということですね。それは確かにそうだと思います。
システムには、種類が少ないが整合性が重要になる更新系操作と、種類が多く形がバラバラの読み取り操作の２種類がある、というのも、感覚に合います。
・「一つのモデルで両方をこなすな」という点も理解しますが、ではどうすればいいのでしょうか？三焦経の操作は参照系の操作として個々の独自参照を独立して実装し、更新系も同様に整合性に気を付けて実装せよ、というざっくりした主張を言っているのでしょうか？
・これがイベントソーシングとセットで使われることが多い、とのことですが、その理由はなぜでしょうか？飛躍していて行間がわかりませんでした。
・イベントソーシングは、初耳だったのですが、追記を重ねて、間違えたら取り消しを追加する、という世界観なのですね。証券系システムでも、一日の取引履歴を記録しておいて、一日の終わりにそれらを集計して残高を更新する、みたいな操作があると聞いています　　なんだか、この概念って、DBのredoログとかWALとか呼ばれるが概念に近いですね。

## 「2軸しかない」について

この気づきから、オントロジーの5要素をもう一度導き直せます。

- **種類の軸**：Object。その内部の構造が Property と Link です
- **操作の軸**：CQS に従って「書く」と「読む」に分けると、書くほうが Action、読むほうが Function です

第1部では、5要素を「時間 × 項数」の2軸から導きました。今回は「種類 × 操作」の2軸に、さらに操作を CQS で2つに割る、という別の経路で同じ5つにたどり着いています。違う経路で同じ結論に着くということは、この5つの切り分けが恣意的なものではないことの傍証になります。

## 1. DDD を基準にしてオントロジーを理解すべきか

**半分はそうすべきで、半分は違います。** DDD はオントロジーの親の一人ですが、唯一の親ではありません。親はおおむね次の3人です。

| 親 | オントロジーが受け継いだもの |
|---|---|
| **DDD** | モデルの**作り方**。業務の専門家と対話して、業務の言葉でモデルを作る |
| **データ統合**（DWH、マスタデータ管理、BI のセマンティックレイヤー） | モデルの**置き場所**。既存システムのデータをつなぎ、「一つの現実に一つの実体」を作る |
| **CQRS** | 動詞の**分け方**。書き込み（Action）と読み取り（Function）を分ける |

DDD だけを基準にすると、2番目のデータの側が抜け落ちます。境界づけられたコンテキスト以外にも、DDD との違いは次のようにあります。

| | DDD | 業務オントロジー |
|---|---|---|
| 対象 | **これから作る**ソフトウェア | **すでにある**データとシステム |
| モデルがある場所 | コードの中（クラス） | コードの外にある宣言的な定義。画面で閲覧できる |
| 誰が読むか | 開発者 | 業務担当者、開発者、LLM |
| 読み取り | 集約がカプセル化する | すべて公開する |
| 範囲 | 1つのコンテキスト | 組織全体（を目指す） |
| 性格 | **方法論**（どう考えるか） | **成果物と実行基盤**（何が存在して動くか） |

おすすめの使い分けは、**ヒアリングとモデリングの進め方は DDD を基準にし、出来上がったモデルをどこに置いて何につなぐかはデータ統合の側から理解する**、というものです。第2部のチュートリアルは、まさにこの順番（ヒアリング → 分類 → データにつなぐ）になります。

用語の対応表も付けておきます。

| DDD | オントロジー |
|---|---|
| ユビキタス言語 | 原則A（業務の語彙で名付ける） |
| エンティティ | Object |
| 値オブジェクト | Property |
| 集約 | Action のトランザクション境界 |
| ドメインサービス | Action |
| ドメインイベント | Action の実行履歴 |
| 境界づけられたコンテキスト | （対応なし。原則C で名前を分けて代替する） |

## 2. CQRS：「一つのモデルでやるな」なら、どうするのか

「それぞれ独立に、気をつけて実装せよ」というざっくりした主張ではなく、**具体的な構造**があります。

```
    コマンド（流用する、約定する）         クエリ（画面、帳票、ダッシュボード）
            │                                    ▲       ▲       ▲
            ▼                                    │       │       │
   ┌──────────────────┐                  ┌──────┐ ┌──────┐ ┌──────┐
   │  書き込みモデル     │   変更を伝える    │読み取り│ │読み取り│ │読み取り│
   │  正規化されている   │ ───────────────▶ │モデルA │ │モデルB │ │モデルC │
   │  業務ルールを検証   │                  └──────┘ └──────┘ └──────┘
   │  唯一の「真実」     │                  用途ごとに非正規化した、読み取り専用の表
   └──────────────────┘
```

- **書き込みモデル**：業務ルールをすべてここで検証します。真実を変えられるのはここだけです
- **読み取りモデル**：画面や帳票ごとに、そのまま表示できる形に整えた表です。利用者は直接書き込みません
- **二つをつなぐもの**：書き込みが起きたら、読み取りモデルを更新する仕組みが必要になります

どこまで分けるかには段階があります。

| 段階 | 分け方 | 身近な例 |
|---|---|---|
| 1 | コード上で、更新処理と参照処理を分ける。DB は同じ | 更新系と照会系で、サービスやクラスを分ける |
| 2 | 読み取り専用の表を別に持つ。DB は同じ | Oracle のマテリアライズドビュー |
| 3 | 読み取り専用の DB を別に持つ | Active Data Guard、リードレプリカ |
| 4 | 業務システムを別に持つ | **勘定系（OLTP）と情報系（DWH）の分離＋夜間 ETL** |

段階4を見ると分かるとおり、**従来の業務システムでは、CQRS をシステム全体の規模ですでにやっています**。勘定系は整合性が命の書き込みモデル、情報系は多様な分析のための読み取りモデル、夜間バッチがその間をつなぐ伝達路です。CQRS は、同じことを一つのアプリの中で、より細かい粒度で行うための考え方だと捉えてください。

## 3. なぜイベントソーシングと組み合わせるのか

行間を埋めます。鍵は、上の図の「**変更を伝える**」矢印です。

読み取りモデルを分けると、次の3つの要件が出てきます。

1. 書き込みが起きるたびに、**何が変わったのか**を読み取り側に伝えたい
2. 読み取りモデルは後から増える。新しい帳票ができたら、**過去の分まで含めて**作りたい
3. 「先月末時点の残高」「この予算は何回流用されたか」のように、**履歴が必要な読み取り**もある

状態を上書きして保存する普通の方式では、2と3が満たせません。上書きした時点で、過去の情報は失われているからです。**上書き保存は、情報を捨てる圧縮**です。

そこで、状態ではなく「起きた出来事」を追記だけで保存すると、次のようになります。

- 1 → 出来事そのものを読み取り側に流せばよい
- 2 → 新しい読み取りモデルは、出来事を最初から再生すれば作れる
- 3 → 履歴はすべて残っている

逆に、イベントソーシングには弱点があります。「今の残高はいくらか」を知るだけでも、全イベントを再生する必要があるため、**読み取りがとても苦手**です。そこで、読み取り用のモデルを別に用意する CQRS が必要になります。

つまり、この二つは**互いの弱点を埋め合う関係**です。

| | 単独で使ったときの弱点 | もう一方がそれをどう補うか |
|---|---|---|
| CQRS | 読み取りモデルへ変更を伝える仕組みが要る | イベントソーシングが、変更の流れそのものを提供する |
| イベントソーシング | 現在の状態を読むのが苦手 | CQRS が、用途別の読み取りモデルを提供する |

数式で書くと、構造がはっきりします。

$$
\text{状態}_n = \mathrm{fold}(\text{apply},\ \text{初期状態},\ [e_1, e_2, \dots, e_n])
$$

読み取りモデルとは、**同じイベント列に対して、違う畳み込み関数を適用したもの**です。残高を作る関数、月別集計を作る関数、流用回数を数える関数、というように。物理で言えば、イベントは各時刻の増分で、状態はその積分です。積分値（状態）だけを取っておいても、元の時間変化（履歴）は復元できません。増分をすべて取っておけば、どんな汎関数でも後から計算できます。前回お話しした「プロジェクション（射影）」とは、この一つ一つの汎関数のことです。

## 4. 証券システムと WAL について

### 証券の日次処理

お聞きになっている処理は、まさにこの構造です。

- 日中：**約定**が次々と記録される（イベント）
- 約定の訂正や取消は、元の記録を消さずに、訂正や取消の記録を**追加する**
- 夜間バッチ：約定を集計して、**残高・建玉・預り金**を更新する（プロジェクションの作成）

ただし、実際の証券システムの多くは「純粋な」イベントソーシングではありません。残高テーブル自体も保存され、それが他の多くの処理の正本になっています。「約定の記録は残しつつ、状態も保存する」という、イベントソーシング的な設計だと理解してください。

### redo ログ・WAL との類似

**鋭い指摘で、実はまさにそのとおりです。** データベースの内部は、イベントソーシングそのものの構造をしています。

| DB の内部 | イベントソーシング |
|---|---|
| redo ログ / WAL（追記のみ） | イベントストア |
| データファイル上のテーブル | 状態（ログを適用した結果） |
| クラッシュ後のリカバリ（redo を再適用） | イベントの再生 |
| Data Guard、ストリーミングレプリケーション | ログを送って別の場所で状態を作る |
| Active Data Guard（読み取り専用の複製） | CQRS の読み取りモデル |
| GoldenGate などの CDC（redo から変更を取り出して配信） | イベントを読み取り側へ伝える仕組み |

この見方は有名で、Kafka の開発者である Jay Kreps のエッセイ「The Log」（2013）や、Pat Helland の論文「Immutability Changes Everything」（2015）は、**「ログこそが真実で、テーブルはログのキャッシュにすぎない」**と主張しています。インフラ側から見えている Oracle の仕組みは、アプリ側の設計思想と同じ形をしている、ということです。

一つだけ決定的な違いがあります。**記録している言葉**です。

```
WAL:              ブロック 0x3F2A のオフセット 128 を 0x00 → 0x7B に変更
イベントソーシング:  予算A から 予算B へ 100万円を 流用した（実行者：田中、理由：…）
```

WAL は物理的な変更を記録していて、業務の意味を持ちません。イベントソーシングは、同じ「追記のみのログ」を**業務の言葉で**書いたものです。ここで話がオントロジーに戻ってきます。

> イベントソーシング ＝ WAL を、ユビキタス言語（業務の語彙）で書いたもの

オントロジーで Action を実行すると、その記録は「誰が、いつ、どの Object に、どの Action を、どんな引数で実行したか」という、業務の言葉で書かれたログになります。
