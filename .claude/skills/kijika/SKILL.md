# 記事化 — 対話を dia-logos の記事に変換する

この会話を、ブログ記事の Markdown に変換して `src/content/posts/` に書き出す。
ルールはここに固定されている。ユーザーは毎回内容を指示しなくてよい。

## 元ネタの2つの経路（棚卸しの優先順位）

記事の素材＝過去の対話は保存場所が2つに分かれている。詳細は CLAUDE.md 参照。

- **claude.ai（Webのチャット）**＝ユーザーの思想が主にここにある。**棚卸しはこちらを優先**。
  `conversations.json` を Export → `node scripts/split-export.mjs` で分割 → 一覧から選んで記事化。
- **Claude Code のローカル履歴**（`~/.claude/projects/**.jsonl`、このセッション含む）＝実務指示が多い。
  **後追い**で良い会話だけ拾う。Claude がその場で読めるので Export 不要。

いずれの経路でも、変換ルール（下記）は同一。

### ⚠ 本文は必ず `content` から取る（`text` は思考が混ざっている）

`conversations.json` の各メッセージには `text` と `content` があり、**中身が違う**。

| フィールド | 中身 |
|---|---|
| `text` | **Claude の英語内部思考 ＋ 日本語応答が連結されたもの**（汚染されている） |
| `content` | **ユーザーに実際に返した応答だけ**（＝クリーン。**こちらが正**） |

**`content` を使えば、英語思考の剪定は不要**。エクスポートが最初から分離してくれている。

3本目（ローマ×AI時代）で、`text` を使って「日本語の比率が高い段落から切り出す」という
当て推量の剪定をやった結果、応答の書き出し（「順番に行きます。」等）を削り落とし、
発話の区切りも崩した。**推測で切るな。`content` を読め。**

- ユーザー発言も `content` を使う（`text` と同内容だが、統一しておく）。
- **`content` が空のときだけ**エクスポートの欠落を疑う。実際 1 メッセージで発生した
  （`text` に英語思考だけが残り、応答本文が消えていた）。その場合は**黙って捨てず、
  ユーザーに「ここが欠落している」と報告**する。元のチャット画面には残っているので、
  貼ってもらえば復元できる。

## 出力先とファイル名

- 保存先: `src/content/posts/`
- ファイル名: `YYYY-MM-DD-<英小文字ケバブのslug>.md`
  - 日付は会話の日付（分からなければ今日）。slug は内容を表す短い英語。

## front matter（必須スキーマ。`src/content/config.ts` と一致させる）

```yaml
---
title: <日本語の表題。結論やテーマが一目で分かるもの>
date: YYYY-MM-DD
summary: >-
  <結論の要約。これ単体で読めて、同時に本文への目次になる。
   「何を選び取ったか」を書く。バズ狙いの誇張はしない。分量は下記の目安に従う。>
notes: |
  <任意。「要点」＝内容そのものの結晶。下記参照。markdown が書ける（箇条書き・強調・見出し）。>
tags: [<テーマ2〜4個。日本語可。既存記事のタグと表記を揃える>]
draft: false
---
```

### 記事は3層構造（4本目で2層から拡張した）

当初はサマリー（索引）と軌跡（過程）の2層だったが、長い対話を記事化してみて、
**内容そのものを持ち帰る場所がない**ことが分かった。ユーザーの言葉で言うと
「軌跡とは別に、内容そのものに対する興味深さもあって、要約と本文の間くらいの粒度のものが欲しい」。

| 層 | front matter / 本文 | 役割 | 主な読者 |
|---|---|---|---|
| **サマリー** | `summary` | **何の話だったか**（索引。後で自分が思い出すため） | 主に自分 |
| **要点** | `notes`（任意） | **何が分かったか**（内容の結晶。構造化された学び） | 読者と自分 |
| **軌跡** | 本文 | **どう考えたか**（生の対話。迷いや反論を含む過程） | 主に他者 |

**`notes`（要点）を書くときの原則:**
- **議論の要約ではなく、内容の結晶**。「Aと言ったらBと返ってきた」ではなく、「結局こういう構造だと分かった」を書く。
- 箇条書き・対応表など、**構造として持ち帰れる形**にする（markdown が使える）。
- **ユーザー自身が対話後に整理したメモがあれば、それを最優先で使う**（4本目はまさにそうした）。
  それはユーザーの理解の構造そのもの＝「何をどう選び取ったか」の直接の証拠であり、価値が高い。
- **要点は単独で読めなければならない。** 判断基準は「内輪の用語かどうか」ではなく、
  **「文脈なしに読んで伝わるか」**。伝わらない語だけを言い換える。
  - 言い換えるべき例：「バケツA/バケツB」——対話中に生まれた即席の呼び名で、文脈がないと
    何のことか分からない（実際ユーザーから指摘を受けた）。「既存の役割をそのまま渡す」
    「希少性の制約を外して構造ごと作り直す」のように、内容が分かる言葉にする。
  - **残してよい例**：「観客席 vs 舞台」「無私の第三者」のように、**その場で生まれた語でも、
    単独で読んで意味が立つ比喩**。これらは対話の成果そのものなので、**平易化の名目で潰さない**。
    機械的に「造語だから言い換える」とやると、的を射た表現まで矯正してしまい、情報量が下がる。
  - 軌跡は原文のまま、要点は単独で通じる形で——という役割分担。
- **タイトルと要点を対応させる。** タイトルが「がんとは何か」と言っているのに要点が
  セキュリティの話だけ、というズレが実際に起きた。**タイトルが約束した内容は、要点でも扱う。**
- 短い対話や、要点として立つ内容がない対話では**省略してよい**（任意フィールド）。

### summary の分量は本文の長さに比例させる

**短い対話の要約の書き方を、長い対話にそのまま適用すると圧縮しすぎて意味が通らなくなる**
（3本目で実際に起きた。ユーザーですら「ギリギリわかるかどうか」と言った）。目安：

| 本文（軌跡）の分量 | summary の分量 |
|---|---|
| 〜3千字（短い一往復など） | 2〜4文 |
| 〜1万字 | 5〜8文 |
| 1万字以上（長大な対話） | 10文以上。節ごとに1〜2文を割り当てるつもりで書く |

**要点を詰め込むのではなく、取り上げる要点を絞って、その一つ一つを噛み砕いて書く。**
論点を全部並べて各1行にすると、圧縮されすぎて誰にも読めない。
「後で自分がこの対話を思い出すための索引」として機能するかを基準に判断する。

### summary を書くときの厳守事項（2本目・3本目で連続してやらかした）

**summary はユーザーの主張の言い換えである。勝手な再解釈を混ぜない。**
剪定は許されるが**歪曲は許されない**。実際にやった歪曲：

- 2本目「スタック接続」：ユーザーが一言も言っていない「人間社会は*上から下へ*積み上げた」という
  構造を創作し、アナロジーの向きを逆にした。
- 3本目「ローマ」：「ローマはAI時代の予行演習ではないか」と書いた。**主客が逆**。ユーザーの起点は
  AI時代の不安であり、ローマはそれを考えるために参照した**補助線**。主役を取り違えた。

**特に「何が問いの起点か」を取り違えるな。** ユーザーが何を出発点にして、何を参照物として
持ち出したのかを、原文で確認する。参照物のほうを主役にすると論旨が反転する。

- 要約する前に、ユーザーの原文をもう一度読み、**その人が実際に使った構造・比喩・方向・起点**を確認する。
- 特にアナロジーは**向き・階層・始点**を取り違えやすい。「何と何が、どちらからどちらへ、どう接続したか」を
  原文どおりに書く。分かった気になって滑らかな一文にまとめると、たいてい歪む。
- 自信がなければ、要約せず**原文の言葉をそのまま使う**方が安全。
- **要約に入れる必要のない論点は落とす**。本文にあるからといって全部を summary に詰めない
  （3本目の「衰退ナラティブへの史料批判」は、要約には不要だとユーザーが判断した）。
- なお **Claude の解釈がユーザーのイメージとズレた場合、そのズレは本文に残してよい**（消さない）。
  ズレたという事実自体が軌跡であり、丸めて一致させると情報量が下がる。歪めてはいけないのは
  「ユーザーの主張の要約」であって、「Claude が実際にそう解釈した」という記録ではない。

## 本文＝軌跡（生に近く。ここが他者にとっての情報量）

- **編集方針は「軽い剪定のみ」。丸めない。** 論理の流れ・迷い・反論・逡巡はそのまま残す。
  平均に均すと情報量が下がる、というのがこのブログの思想。
- 構成は対話の実際の流れに沿う。無理に整形しない。節見出し（`## …`）は
  流れの区切りにだけ付ける。相手の重要発言は引用（`>`）で残してよい。
- コードブロック・表・リンクはそのまま活かす。
- **アナロジーを含む対話なら、その骨格を潰さない**。ユーザーは異分野間の構造的相似を
  発見するのが得意で、それ自体が特徴。どの分野とどの分野を、どんな構造で橋渡ししたのかが
  読者に伝わるように書く。この場合 tags に `アナロジー` を付ける。（詳細は CLAUDE.md の「2軸」）
- **可読性のためのリード文の太字化は可**。文中に埋もれた論点の頭（例「まず賛成する部分。」）を
  `**…**` で立たせてよい。1本目のフィードバックで「見やすい」と承認済み。ただし語句の
  追加・言い換えはしない（あくまで既存の文の強調にとどめる。丸めとは区別する）。

### 会話の分量による本文の扱い（要・今後の詰め）

1本目は短い一往復だったので「問い→応答」で素直に収まった。**大ボリュームの回**（数十msg）を
どう構成・要約するかは未確定の課題。当面は流れに沿って節見出しで区切るが、冗長になりすぎる場合の
方針（間引き・小見出しの粒度・サマリーの長さ）は記事を作りながら詰める。→ このループで改良していく。

## 剪定ルール（完全公開ゆえ必須・妥協しない）

このブログは認証なしの完全公開。以下は**必ず**除去・置換する:

1. **個人を特定する情報**: 実名（本人・家族・第三者）、住所・地名で自宅が割れるもの、
   メールアドレス、電話番号、勤務先の非公開情報、子どもの生年月日など。
2. **ファイルパス・環境固有の情報**: ローカルの絶対パス、内部URL、認証情報、
   マシン名、リポジトリの非公開詳細。
3. **本人がまだ人に見せたくない逡巡**: 判断に迷ったら残さず、要約に留めるか落とす。
4. **他プロジェクトの秘匿情報**: この会話に混ざった別件の未公開情報。

除去して意味が通らなくなる箇所は、一般化した表現に置換する
（例: 具体的な地名 → 「ある地方都市」）。**迷ったら消す**。

### 仕事の話は「削除」ではなく「当事者性の除去＝一般論化」で扱う（4本目で確立）

ユーザーは実務（ITシステム／セキュリティ）の知見を対話に持ち込むことがある。ここを丸ごと削ると
議論の筋が死ぬ。一方そのまま出すと勤務先の内部構成が漏れる。**線引きは「一般にそう言えること」と
「私が担当しているシステムの話」の境界**にある。当事者性だけを抜き、技術的中身は残す。

| 消す（当事者性・帰属が割れる） | 残す（一般論として成立する） |
|---|---|
| 「**私のシステムでは**」「うちの」 | 「一般に IT システムでは〜」 |
| 業種の特定（例: **金融**システム） | 業種を言わない |
| 自社固有の構成・呼称（例: **GWサーバ**） | 一般的な言い換え（例: 閉域網で接続している他システム） |
| 現行構成の弱点・これからどう直すか | 設計原理・一般的なゾーン設計論 |
| 「**この製品を入れる**」「入れたら楽」 | 「対応するセキュリティの実装例は〜」「導入に比較的有利」 |

- **DMZ / Trust のような教科書的な一般概念は残してよい**。危ないのは自社固有の構成と、
  それを今どう変えようとしているか（＝現状の弱点の開示）。
- 製品名に触れるときは**中立**に。導入を検討している当事者に見えないようにする
  （攻撃面の情報になるうえ、勤務先の調達を示唆してしまう）。

## 手順

1. 会話全体を読み、主題と「何を選び取ったか」を特定する。
2. front matter を作る（summary は結論＝目次として書く）。
3. 本文＝軌跡を、上記の剪定を施しつつ生に近い形で書き出す。
4. `src/content/posts/YYYY-MM-DD-<slug>.md` に保存する。
5. 保存後、ユーザーに **剪定した項目を箇条書きで報告**し（何を落としたか透明にする）、
   確認のうえ `git add -A && git commit && git push` するかを尋ねる。
   push すると Cloudflare Pages が自動ビルドして公開される。

## 迷ったときの原則

- 読まれ方を最適化しない。差し出して回るものではなく、興味を持って訪ねてきた人が
  読んで受け取るために置いてあるもの。だから広告ではないし、押し出しもしない。
- 日付は「その時点の私」のスナップショット。後から思想が変わっても記事は直さない。
- 剪定と誇張は別物。個人情報は削るが、思考の生々しさ・迷いは削らない。
